# pg_permissions documentation site

The Astro + Starlight site publishes application guides, API reference, and research for `pg_permissions`. Canonical prose lives under `../pg_permissions`. Edit those files, not the generated site pages.

```bash
make docs              # install if needed, build, and check links/content
make docs.dev          # local development server
# or, from docs/:
npm run sync           # regenerate pages, Markdown exports, and data
npm run build          # sync, build, and validate
npm run check:quickstart # execute the quickstart in a temporary Postgres
```

The site uses Astro 7, Starlight 0.42, and `starlight-links-validator`. Charts are build-time SVG components. Use the Node version required by the installed Astro release.

## Page inventory and navigation

`navigation.mjs` is the source of truth for source paths, routes, labels, and sidebar groups. Both `astro.config.mjs` and `scripts/sync.mjs` import it. Add new pages there and put their Markdown under `pg_permissions/docs/` or `pg_permissions/research/`.

Task guides cover setup and examples. Model guides share a structure while preserving each model's own concepts. The reference is organized by model, with current-subject helpers beside the other functions. Research keeps historical designs separate from current application guidance.

`content-migration.json` records where the original sections moved and the old inbound anchors. Compatibility pages retain old paths and headings, link to the current pages, and use `pagefind: false` so they do not compete with current guides in search. Keep these pages when adding or moving material; the extension's condition error hint still names `docs/conditions.md`.

## Generated files

| Path | Source | Tracked? |
| --- | --- | --- |
| `src/content/docs/**/*.md` | Canonical Markdown listed in `navigation.mjs` | No |
| Guide directories under `src/content/docs/` (`models`, `integrations`, `reference`, `rls`, `get-started`) | Generated `.md` or `.mdx` when a page uses tabs | No |
| `src/content/docs/index.mdx` and research chart/comparison `.mdx` pages | Hand-written site components | Yes |
| `public/markdown/**/*.md`, `public/llms.txt` | Plain Markdown exports and an agent index | No |
| `src/data/bench/*.json` | Benchmark run files | No |
| `src/data/workloads.generated.json` | First sentence of each workload SQL header | No |
| `src/data/fixture/*.json` | Fixture generated by `npm run fixture` | Yes |
| `src/data/workload-labels.json` | Human-readable workload labels and groups | Yes |

Every generated site page has a marker and an edit link to its canonical source. The sync step removes stale generated pages. New directories with generated MDX need an entry in `.gitignore`; keep hand-authored MDX outside those directories.

Adjacent fenced blocks with `tab="SQL"` and `tab="JavaScript"` become synchronized Starlight tabs. GitHub and plain Markdown exports retain both blocks. Do not hand-copy a second language version into another guide.

## Sync and deployment

Sync runs before development and build. It adds page metadata, rewrites relative links, exports plain Markdown, copies benchmark data, and extracts workload descriptions. Links to code and other non-page files point to GitHub. Missing targets produce a warning; resolve warnings before publishing.

Set `DOCS_REPO_URL` and `DOCS_REPO_REF` for source and edit links. The defaults are `kiwicopple/pg-extensions` and the `pg_permissions` branch. Set `DOCS_SITE` to the deployment origin and `DOCS_BASE` when hosting below a path, for example `/pg-extensions`. Markdown and index links honor the same base.

The plain Markdown exports preserve the source code fences without tab markup. `llms.txt` lists canonical pages and their descriptions; compatibility pages are exported for old links but omitted from that index. The homepage links to the index. Historical records retain their status notes.

## Validation

`npm run build` checks rendered links and fragments, Markdown export links and code preservation, old inbound anchors, sidebar routes, and coverage of all 26 public SQL functions.

`npm run check:quickstart` runs the SQL fences directly from the quickstart in an isolated Postgres cluster, then checks the visible rows and transaction-local identity. It needs Postgres binaries (`PGBIN` can select them). The existing usage specs cover the longer walkthroughs:

```bash
../pg_permissions/test/run.sh usage
```

When moving a section, check its prerequisite data and the order of model or policy changes. Update the matching usage-spec comments. Keep intentional error examples separate from scripts that stop on errors.

## Benchmark data

Pages read every run file with `import.meta.glob` (`src/lib/bench.ts`). Shape of a run file: see `src/lib/bench.ts` (`Run`): `run_id, date, environment, host, pg_version, design, scale, shape, clients, duration_s, workloads[], seeds[], checksums{}`.

- **Real data wins.** If `src/data/bench/` has any file, only real data is used. Otherwise the fixture in `src/data/fixture/` is used and the pages say so.
- **Tags.** A run's `tag` (JSON field, else the run_id suffix after the fifth dash) names a variant of the engines, e.g. `opt` for the session 3 optimized engines. Tagged and untagged runs of one configuration are different series; a tagged run never replaces an untagged one.
- A **series** is one Postgres major version on one environment with one tag (for example "PG 18 (docker, optimized)" or "PG 16 (local)"). `allSeries` in `src/lib/bench.ts` groups by environment, major and tag.
- **Primary series** (dashboard, home page): set by `PRIMARY_PREFERENCE` in `src/lib/bench.ts`. It is Docker PG 18 `opt` if that exists, else the newest Docker series, else the newest local series. It is never chosen by run count. Charts that need scales Docker lacks (scaling from 10k to 1M) use `scalingSeries()` (today local PG 16) and say so in their subtitle; no chart mixes environments or tags.
- The **Postgres versions** page compares only series with the same environment and tag: optimized Docker first, then pre-optimization Docker.
- The **Optimizations** page (`src/lib/optimizations.ts`, `src/components/opt`) pairs the untagged and `opt` Docker series per Postgres version (main version 18): dumbbell charts (hollow dot before, filled dot after, log axis), a ranking table (engines within 20% of the best are tied) and takeaways computed from the numbers.
- Takeaways under each chart are computed from the data at build time, so they stay true when numbers change.
- A malformed file is skipped with a warning, not a build failure.

## Charts

Build-time SVG from Astro components in `src/components/viz` (no client-side chart library). The only client JS is a small script for the tooltip and the scale/shape tabs; without it every value is still in the SVG labels, the `Table view` under each chart and, for tabs, all panels are shown. Colors follow the dataviz skill: one fixed color per engine (A blue, B orange, C aqua, categorical slots 1 to 3, validated for color-blind separation in light and dark), thin marks, a legend plus direct labels, light/dark via Starlight's theme attribute (`src/styles/viz.css`).

## Link checking

`starlight-links-validator` checks absolute links and anchors. Synced pages use relative links, which that plugin skips, so `npm run build` finishes with `scripts/check-links.mjs`, which resolves every internal href and `#anchor` in `dist/` and fails the build on a broken one.
