# Research docs site

One site for the research records of every extension in this repository: design records, benchmark reports, reviews and build journals. It is built with Astro + Starlight and deployed to GitHub Pages at https://kiwicopple.github.io/pg-extensions/ by `.github/workflows/research-docs.yml` on every push to `main` that touches research.

User documentation stays on each extension's own site (for example https://permissions.dev for `pg_permissions`). Research is internal development material, so it lives here instead.

## Convention: `<extension>/research/`

Put an extension's research Markdown in `<extension>/research/`, with a `README.md` as its overview. That is all. The sync step finds every top-level directory with a `research/` directory, and the extension appears on the landing page and in the sidebar under `/<extension>/`:

- `research/README.md` becomes `/<extension>/`, the extension's index.
- Every other Markdown file becomes a page at its path, lowercased: `research/benchmarks/run-1.md` becomes `/<extension>/benchmarks/run-1/`. A `README.md` in a subdirectory becomes that directory's page.
- The sidebar group is generated from the directory tree, with page titles from each file's `# heading`.

Keep writing for GitHub: use relative links. At build time links between research pages become site links, links into `<extension>/docs/` go to the extension's user site (when one is configured), and links to any other file in the repository (code, `bench/`, `test/`, scripts) go to GitHub.

### Optional: `research/navigation.json`

To choose the routes, labels and sidebar order, add `research/navigation.json` (see `pg_permissions/research/navigation.json`):

```json
{
  "title": "pg_permissions",
  "userSite": "https://permissions.dev",
  "pages": [{ "src": "README.md", "route": "", "label": "Overview" }, { "src": "journal.md", "route": "journal", "label": "Build journal" }],
  "sidebar": [{ "label": "Overview", "slug": "" }, { "label": "Group", "collapsed": true, "items": [{ "label": "Build journal", "slug": "journal" }] }]
}
```

- `src` is relative to `research/`; `route` and `slug` are relative to `/<extension>/`, and `""` is the index. Only listed files are published; the sync warns about Markdown files that are left out (links to them go to GitHub).
- `historical: true` prefixes the page title with "Historical:".
- `userSite` is the extension's user documentation. Links into `<extension>/docs/` use the routes in `<extension>/site/navigation.mjs` (its `pages` export).
- The extension's user site may link to research pages; `pg_permissions/site/research-links.mjs` reads the same file, so both sites agree on the URLs.

### Optional: hand-written pages and data

Pages that need components (charts) are `.mdx` files under `src/content/docs/<extension>/`, and their components, data and styles live in `src/extensions/<extension>/`. Stylesheets in `src/extensions/<extension>/styles/` are loaded on every page. If `src/extensions/<extension>/sync.mjs` exists, the sync step calls it with the extension directory, for data the pages need at build time. Link to a hand-written page from research Markdown by its path in the repository; the sync turns that into a site link.

## Build and preview locally

```bash
# from the repo root
make research.docs        # npm ci (first time), sync, build into research-site/dist, check links
make research.docs.dev    # local development server with hot reload
# or from research-site/
npm ci
npm run dev               # sync, then serve at http://localhost:4321/pg-extensions/
npm run build             # sync, build and check links
npm run preview           # serve the built site
```

The site defaults to `DOCS_SITE=https://kiwicopple.github.io` and `DOCS_BASE=/pg-extensions`; set them to host elsewhere (the workflow sets them from `actions/configure-pages`). `DOCS_REPO_URL` and `DOCS_REPO_REF` set source and edit links (defaults: `kiwicopple/pg-extensions`, `main`).

## Generated files

| Path | Source | Tracked? |
| --- | --- | --- |
| `src/content/docs/**/*.md` (including `index.md`, the landing page) | `<extension>/research/**/*.md` | No |
| `src/content/docs/<extension>/**/*.mdx` | Hand-written pages | Yes |
| `src/extensions/pg_permissions/data/bench/*.json` | Benchmark run files, copied from `pg_permissions/bench/baselines/data` | No |
| `src/extensions/pg_permissions/data/workloads.generated.json` | First sentence of each workload SQL header | No |
| `src/extensions/pg_permissions/data/fixture/*.json` | Fixture generated by `npm run fixture` | Yes |
| `src/extensions/pg_permissions/data/workload-labels.json` | Human-readable workload labels and groups | Yes |

Every generated page has a marker and an edit link to its source. The sync step removes stale generated pages and never touches hand-written `.mdx`.

## Validation

`npm run build` runs `starlight-links-validator` (absolute links, anchors, sidebar) and then `scripts/check-links.mjs`, which resolves every internal href and `#anchor` in `dist/` (the synced pages use relative links, which the plugin skips) and fails the build on a broken one.

## pg_permissions charts

The benchmark dashboard, optimizations, Postgres versions and prototype comparison pages are hand-written `.mdx` pages in `src/content/docs/pg_permissions/`. Their code is in `src/extensions/pg_permissions/` (paths below are relative to it).

### Benchmark data

Pages read every run file with `import.meta.glob` (`lib/bench.ts`). Shape of a run file: see `lib/bench.ts` (`Run`): `run_id, date, environment, host, pg_version, design, scale, shape, clients, duration_s, workloads[], seeds[], checksums{}`.

- **Real data wins.** If `data/bench/` has any file, only real data is used. Otherwise the fixture in `data/fixture/` is used and the pages say so.
- **Tags.** A run's `tag` (JSON field, else the run_id suffix after the fifth dash) names a variant of the engines, e.g. `opt` for the session 3 optimized engines. Tagged and untagged runs of one configuration are different series; a tagged run never replaces an untagged one.
- A **series** is one Postgres major version on one environment with one tag (for example "PG 18 (docker, optimized)" or "PG 16 (local)"). `allSeries` in `lib/bench.ts` groups by environment, major and tag.
- **Primary series** (dashboard): set by `PRIMARY_PREFERENCE` in `lib/bench.ts`. It is Docker PG 18 `opt` if that exists, else the newest Docker series, else the newest local series. It is never chosen by run count. Charts that need scales Docker lacks (scaling from 10k to 1M) use `scalingSeries()` (today local PG 16) and say so in their subtitle; no chart mixes environments or tags.
- The **Postgres versions** page compares only series with the same environment and tag: optimized Docker first, then pre-optimization Docker.
- The **Optimizations** page (`lib/optimizations.ts`, `components/opt`) pairs the untagged and `opt` Docker series per Postgres version (main version 18): dumbbell charts (hollow dot before, filled dot after, log axis), a ranking table (engines within 20% of the best are tied) and takeaways computed from the numbers.
- Takeaways under each chart are computed from the data at build time, so they stay true when numbers change.
- A malformed file is skipped with a warning, not a build failure.

### Charts

Build-time SVG from Astro components in `components/viz` (no client-side chart library). The only client JS is a small script for the tooltip and the scale/shape tabs; without it every value is still in the SVG labels, the `Table view` under each chart and, for tabs, all panels are shown. Colors follow the dataviz skill: one fixed color per engine (A blue, B orange, C aqua, categorical slots 1 to 3, validated for color-blind separation in light and dark), thin marks, a legend plus direct labels, light/dark via Starlight's theme attribute (`styles/viz.css`).
