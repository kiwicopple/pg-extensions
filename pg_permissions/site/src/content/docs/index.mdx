<span id="what-it-is" />

`pg_permissions` stores roles, sharing relationships and Cedar policies alongside your application data. Your backend can ask Postgres who can do what without calling a separate authorization service. If you want the database to enforce the same rules on a table, use row level security (RLS).

## Check access from your backend

Can Alice read documents in Acme? With a [server client](./integrations/javascript/), set the subject and ask for the permission in that organization. The [quickstart](./get-started/quickstart/) walks through assigning the role and checking two users.

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
const { data: allowed, error } = await permissions
  .as({ id: 'alice' })
  .rbac.hasPermission({ permission: 'documents.read', scope: 'acme' })

if (error) throw error
if (!allowed) throw new Error('Forbidden')
```

</TabItem>
<TabItem label="SQL">

```sql
begin;
select set_config('permissions.subject_id', 'alice', true);
select permissions.rbac_has_permission(
  permission => 'documents.read',
  scope => 'acme'
);
commit;
```

</TabItem>

## API reference

Look up a method in the [JavaScript client reference](./reference/javascript/), or browse the [shared](./reference/shared/), [RBAC](./reference/rbac/), [OpenFGA](./reference/openfga/) and [Cedar](./reference/cedar/) APIs.

[OpenFGA compatibility](./models/openfga/compatibility/), [Cedar compatibility](./models/cedar/compatibility/), [API limits](./reference/limits/), and [CEL support](./reference/cel/) describe the boundaries of the implementation. A check returns a decision for your backend to enforce. If you add RLS, standalone checks do not include any extra rules defined only in those table policies.
