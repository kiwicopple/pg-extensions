# pg_permissions: Decision guide

Picks no winner among the three engines (see "Session 4 direction" for the direction taken since). It lays out what was built and measured. Every claim cites its source. Numbers come from [`bench/baselines/OPTIMIZATIONS.md`](./bench/baselines/OPTIMIZATIONS.md) (**OPT**: all three engines after the session 3 optimization pass, Postgres 18.6 in Docker). Cross-version results are in [`bench/baselines/VERSIONS.md`](./bench/baselines/VERSIONS.md) (**VER**), and the pre-optimization numbers (local Postgres 16.4) are in [`bench/baselines/COMPARISON.md`](./bench/baselines/COMPARISON.md) (**CMP**). Test results come from [`GOALS.md`](./GOALS.md), and weaknesses from the design docs [A](./designs/a-tuple-core.md), [B](./designs/b-policy-first.md) and [C](./designs/c-compiled-model.md). Section names are given where a file is long. "Large" is 1M documents, 10k users, 500 teams (OPT, Large default); "medium" is 100k documents. "Deep" and "wide" are medium-scale stress shapes: teams nested 9 levels, and 50 teams per user (VER, shape descriptions).

## Session 4 direction: per-model tables

On 2026-10-29 (session 4) the direction changed: the single generic API is dropped. The A/B/C comparison below stays as the evidence behind the change; it no longer decides between three engines for one API.

1. Per-model table sets. The `permissions` schema holds a separate set of tables for each model, and each set follows an existing spec as closely as possible. `rbac_*` tables are the blessed path, first-class tables rather than wrappers over a core. `fga_*` tables follow OpenFGA. An app can use several models at once for different things. They compose in Postgres RLS: permissive policies are ORed and restrictive policies are ANDed. This is also the graduation path: an app adds the FGA model next to RBAC instead of migrating off it.
2. Why. (a) The usage-doc findings come from forcing different semantics through one API: the `rbac` preset isn't fully identical across engines, and forbid means something different in each (A only against the subject's own tuple, C same-type only, B covers groups; "Findings from writing the usage docs" below, C §9, B Deviations 4). (b) The `rbac` preset is flat across engines (under 1 ms, within about 0.1 ms; OPT, Ranking), and the engines only differ on sharing shapes, where the optimizations are model-specific (B's closures, C's materialized memberships). Per-model tables let each model be optimized for itself. (c) Following a spec lets developers and tools reuse what they already know, and lets us follow spec updates, which a generic layer makes hard.
3. OpenFGA, not SpiceDB or a generic "Zanzibar-style" model. The two have different schema languages, so following a spec means choosing one. OpenFGA was chosen specifically so that its public test suite can be used as a test oracle, and because it has CEL conditions on tuples.
4. First spike. The `rbac_*` tables plus an OpenFGA core subset (direct relations, computed usersets, tuple-to-userset, wildcards `user:*`), run against OpenFGA's own test cases, plus one table whose RLS combines RBAC and FGA, benchmarked against the numbers in this document. OpenFGA conditions (CEL) are a second stage after the core. In pg_tle, CEL means writing a parser and compiler in SQL or PL/pgSQL, which is the largest single cost.
5. Cedar is deferred to a later model (`cedar_*`), with B as the starting point. Full Cedar `when`/`unless` over arbitrary attributes doesn't compile to index lookups (C §9), and B already refuses shapes such as `resource.owner_id == principal.id` (B, Weaknesses), so Cedar will likely be a documented subset tested against Cedar's corpus.
6. No separate ABAC model. ABAC is a category, not a spec; XACML is the only formal standard and nobody builds new systems on it. Row attributes (`status = 'published'`, tenant and owner columns) are covered by RLS, attributes on a relationship (expiry, IP range, amount) by OpenFGA conditions, and policy-language ABAC by Cedar later. One gap stays: row attributes that live only in RLS are invisible to the check functions (A §12.4: `check_for` returns true for a draft that RLS hides). The usage docs must say either that the check functions are advisory and RLS is final, or that row attributes are passed into the check.
7. Shared code is a small toolkit, not an API: subject identity (G1), the plan-time-evaluation guard (the trailing dummy argument with a VOLATILE `_unfolded_null()` default; finding 1 below), `collate "C"` on text ids, and the install and pg_tle plumbing (G14).
8. The prototypes. A is closest to OpenFGA and is the starting point for `fga_*`; C's materialized memberships remain a possible optimization if wide reads need them. B is the starting point for Cedar later. C's generic compiled model is the piece this direction drops. The prototypes stay in the repo as measured history, and `pg_permissions--0.0.1.sql` stays empty until the spike is validated.

The open questions below are annotated with what this changes. Sections that compare the three engines as candidates for one API ("Where things stand" through "Hybrids worth considering") are unchanged.

## Where things stand

Three engines are built as prototypes in [`prototypes/`](./prototypes/): A (tuple core, Zanzibar-style tuples, read-time recursive walk), B (policy-first, Cedar-style policies, closures precomputed on write) and C (compiled model, JSON model, materialized memberships). The extension file itself is still empty. All three pass the shared goals G1-G14 and their own design-specific specs (A 18/18 files and 199 assertions, B 18/18 and 189, C 21/21 and 229; GOALS). They return identical visible-document sets for every read policy, at every scale, shape and Postgres version measured, and the optimizations changed no checksum (OPT, Checksums). The `rbac` preset is the same API and gives the same answers on all three, and its p50 latency stays under 1 ms and within about 0.1 ms across engines (OPT, Ranking: `rbac_check` 0.30 / 0.27 / 0.24, `rbac_select_page` 0.76 / 0.73 / 0.67). So the choice only matters for apps that graduate to per-object sharing.

The optimization pass moved the trade-offs. Compared with the pre-optimization guide (same Docker setup, PG 18; OPT, Before → after):

- **B's nest write** went from 107 to 0.62 ms (4 clients, large). B is now in A's range on writes, not C's. C's went from 300 to 57.7 ms: still the slowest by two orders of magnitude, but 5x better.
- **B's storage** halved (763 to 378 MB at large) and is now below A's (404 MB). C is lowest at large (182 MB).
- **`nest_check`** is a three-way tie (0.31 / 0.32 / 0.30 ms at large).
- **A's wide reads** are no longer an outlier: wide `share_select_page` 125 to 14.4 ms, now 1.8x C's 8.20 instead of 12x. A beats B there (B 17.8) on 17 and 18, but not on 16 (OPT, Ranking).
- **Single-branch parents policy** gaps narrowed: page 45.6 / 13.7 / 4.94 ms for A / B / C (was 240 / 102 / 9.26).
- **Budgets:** at large A misses 3, B 1, C 2 (was 3, 3, 1; OPT, Budgets).

What still separates the engines: the cost of nesting a team (A one row, B closure rows, C membership rows under a global lock), the single-branch policy and wide reads (C leads), storage that depends on the shape (C is largest at medium wide), and how much the policy shape and the data model cost. pg_tle now installs on PG 16, 17 and 18 for all three (G14). Everything was measured on one laptop, in Docker, one run per configuration.

## Choose A if

- Your sharing graphs are shallow and narrow, or you mostly use RBAC. At large with the default shape A's sharing page is 1.03 ms, within 10% of the others, and it meets the session-1 budgets (OPT, Large default; Budgets).
- You want the smallest extension to maintain: 871 lines, 28 functions, no derived data, no drift, no locks, no isolation-level restrictions. This is now A's main edge over B, not nest speed: B's nest is 0.62 ms against A's 0.15 (OPT, Ranking), both far under C's 57.7 ms.
- Team and membership edits are frequent or bulk (directory syncs, big teams being nested) and you don't want any write amplification. A writes one tuple at 23.6k tps with 4 clients. B writes closure rows under a lock held about 0.2 ms for a team of users (6.1k tps), but nesting a sub-tree of many teams writes the product of descendants and ancestors, which wasn't benchmarked (B, Remaining hard limits).
- You want OpenFGA/SpiceDB familiarity (A §1).
- You accept writing the two-arm projection policy (an `org_id` or `folder_id` arm plus a shared-ids arm) for org or folder access.
- It loses on: the single-branch parents policy (45.6 ms page and 75.1 ms count at large, 9x and 6x C; the only engine over those budgets), wide memberships (14.4 ms at 50 teams per user, 1.8x C and, on 17 and 18, ahead of B), and storage at large (404 MB, the most of the three, including a 6.8 MB edge-kind index added by the optimization; A §13.1). Its read cost still grows with what the subject reaches (A §13.3). `rbac_check` got 10-20% slower in every cell (0.26 to 0.30 ms; OPT, Other differences). Before the optimization A's wide page was 125 ms (12x C) and the large single-branch page 240 ms in Docker (221 and 509 ms on local 16.4; Docker runs these paths about 2x faster, VER, Calibration).

## Choose B if

- You need forbid on groups, or conditions evaluated by the engine, in the first year. B is the only engine that has them (B, Deviations 4, 6; PLAN §8 "The real decision").
- Your roadmap is Cedar-like policies (CEL, attribute rules), and a policy table is the natural place.
- Keys are text or bigint rather than uuid (B, Schema: text ids).
- You want generated RLS (`rls_expression`, `apply_rls`), and can live with regenerating it when policies change.
- After the optimization B is no longer the worst on writes or storage, the axes where it used to be. Nesting is 0.62 ms (was 107), storage 378 MB at large (below A's 404, was 763), `nest_check` 0.32 ms (tied), the single-branch page 13.7 ms (2.8x C, 3.3x faster than A) and count 21.6 ms (OPT, Ranking).
- It is the slowest of the three on wide sharing reads (17.8 ms page, 8.41 ms list; C 8.20 and 3.41, A 14.4 and 4.44) and misses the medium wide `share_list_objects` budget (OPT, Budgets). It misses `write_nest_team` at wide (1.47 ms). It is the second largest (1,810 lines, 57 functions, after C's 2,012 and 65).
- Its `can()` and `ids()` are two implementations of one semantics; they agreed on 2,400 random cases, an ad hoc check not committed as a spec (B, Partial evaluation). The optimized closure has the latent delete bug described in the open questions.

## Choose C if

- Reads dominate and group shapes are wide or deep. C's reads barely move between shapes (`share_select_page` 0.66 deep, 8.20 wide at medium) and on wide it is 1.8x faster than A and 2.2x faster than B (8.20 vs 14.4 and 17.8). The lead over A on wide reads shrank from 12x to 1.8x with the optimization (OPT, Ranking), so this is now a smaller reason to pick C than it was.
- You want the single-branch RLS policy (no hand-written `org_id` arm) at large scale. It is 4.94 ms for C against 13.7 for B and 45.6 for A (page), and 11.9 / 21.6 / 75.1 for the count. The projection stays about 4.7x cheaper for C too (1.05 ms; OPT, Large default).
- Nesting teams is rare, or an admin-time action, and a global write lock is acceptable. A nest costs 57.7 ms at large with 4 clients (67 tps; was 300 ms), and C's wide sharing seed took 24.7 s (was 176 s; A 5.9 s, B 12.6 s). `grant_many()` loads the wide seed in about 8 s (C §15.4, local, not in the benchmark seed).
- Your IDs are uuids, and you want typed validation and unknown names that raise on write.
- It has the smallest storage at large (182 MB) but the largest at medium wide (191.6 MB against 97.4 for A and 105.3 for B), because it materializes memberships per user.
- It loses on: the largest and most complex write path (2,012 lines, 65 functions), the only engine whose nest is far over the 1 ms budget at every scale (OPT, Budgets), `repeatable read` refused for lock-taking writes, uuid-only IDs, and the global lock.

## Hybrids worth considering (untested ideas)

None of these has been built or measured.

1. **A's engine with C's materialized memberships behind the same functions.** PLAN §8 notes A and C share almost the same API. This targets the wide and deep reads, but after the optimization the gap is 14.4 vs 8.20 ms on the wide page (was 125 vs 10.2), so the case is weaker. It would also inherit C's global lock, drift risk and the write path that is the bulk of C's code (C §12.1), so it may end up as C without the typed model. Object grants would still take no lock (C §5).
2. **The projection policy as the blessed RLS pattern, whatever the engine.** Write the two-arm form: shared ids or a parent column (`org_id`, `folder_id`). At large it is 1.33 / 1.15 / 1.05 ms (A / B / C), against 45.6 / 13.7 / 4.94 ms for the single branch. B's `rls_expression` already generates this shape. The cost is that org or folder access lives in the policy, so `check` and `list_subjects` on the engine side need the parent links to stay complete (A §12.1). The projection matters less than before: the engine is no longer the bottleneck for B and C on the single branch.
3. **Ship only the `rbac` preset first, and pick the sharing engine later.** The preset's API and answers are identical on all three and its latency is flat (OPT, Ranking), so it could be released on the smallest engine and swapped. The risk is graduation: C's graduation is one `apply_model()` call, B's introduces policies, A's is an extra `or` branch (C §8, B Blessed path, PLAN §6). Whether data would need migrating between engines is not tested.

## What the optimization pass taught

Four findings that apply whatever engine is chosen. They are the reason PLAN §4 gained four rules. The design docs measured each one locally (16.4, 1 client, interleaved); OPT re-measures their combined effect in Docker with 4 clients, not each separately.

1. **The planner runs STABLE functions at plan time.** To estimate the row count of `array(select unnest(f('x'))::uuid)`, the planner evaluates `f` when its arguments are constants (`estimate_expression_value`). Every RLS query ran the whole list function twice. Medium wide planning for A's sharing policy took 11.7-12.8 ms (3,564 buffers) and now takes 0.22 ms (112 buffers, catalog lookups only); B's went from 3.9 to 0.24 ms and C's from 3.2-3.4 to 0.27 ms (A §13.1; B step 7; C §15.8). Marking the functions VOLATILE stops it, but it gives up the statement's snapshot: under read committed a volatile function takes a fresh snapshot per query it runs, so grants can be read at a later instant than the rows they filter (found in B, applied in A and C). The snapshot-safe fix is a trailing argument whose default is a VOLATILE function returning null (`_unfolded_null()`), so the call isn't constant but the function stays STABLE. The cost is an ignored extra parameter in the signature (`boolean` in A and C, `jsonb` in B), and callers who pass every argument as a constant fold it again. Boolean quals (`has_permission`, `can`) and `(select f())::uuid[]` are not pre-evaluated. The first pass missed cases in B (`scopes_with_permission`, and the constant resource condition that `rls_expression` emitted); an EXPLAIN and a call-count probe found them (B step 7; `22_no_plan_time_eval`).
2. **Collation on text ids.** The database default (`en_SG.UTF-8` here) sent every B-tree comparison, join and `distinct` sort of a uuid-as-text through `strcoll`. `collate "C"` on the id columns: B's medium wide `share_list_objects` 24.5-25.3 to 6.8 ms and `nest_check` 2.2 to 0.79 ms (the `distinct` sort of 6.7k ids was 19 of 29 ms); A's wide page 18.1 to 16.2 ms. Equality doesn't change; only array order does. Linux `strcoll` is slower than macOS's, so Docker should gain more (not isolated in OPT). C uses uuid columns and isn't affected.
3. **PL/pgSQL versus SQL re-planning.** A SQL function with a `SET` clause or `security definer` is never inlined, and on Postgres 16 its body is planned again on every call. Moving B's hot wrappers to PL/pgSQL took `rbac_check` from 0.39 to 0.29 ms and `_parent_keys` off 0.08-0.2 ms per call; in Docker B's RBAC reads are 1.2-1.7x faster on 16 and 17 and 1.0-1.2x on 18 (OPT, Other differences; the explanation that 18 caches those plans is OPT's, not verified here). A's `_reach` and C's `_memberships_for` are PL/pgSQL for the same reason ([prototypes/README](./prototypes/README.md); C §15.2). Pinning `plan_cache_mode = force_generic_plan` fixed functions whose custom plans were re-planned every call (B `can()` 0.66 to 0.11 ms), at the price of never picking a hash join for a huge frontier (A §13.3). Set-returning helpers also need a `rows` estimate: B's `_parent_keys` was assumed to return 1,000 rows and the planner hash-joined a seq scan of `ancestors`, taking `can()` from about 1.3 to 17-22 ms.
4. **Closures over containers only.** B's per-document closure rows were the cost behind its nest write and storage. Storing rows only for entities that have children (C already did) took the nest from 107 to 0.62 ms, large storage from 763 to 378 MB and the parents seed from 121 to 45 s. A user's groups are then one hop further, so wide reads got 5-8% slower (B, step 4). C's own nest gain came from a different change, a delta insert instead of a recompute (C §15.1; 300 to 57.7 ms). One caveat: the optimized closure keeps a pre-existing depth-cap bug on delete (open question 8).

Cross-engine observations from OPT worth keeping: Docker and local numbers differ by up to 2x for the PL/pgSQL-heavy paths (VER, Calibration), so the optimization factors measured locally in the design docs (for example A's single-branch page 505 to 35 ms) are larger than Docker's (240 to 45.6 ms), while the after values reproduce within 1.3x (OPT, Claims). Medium wide `share_list_objects` for B improved on 16 (8.96 to 4.47 ms) but not on 17 (9.02 to 9.26) and only partly on 18; this was reproduced and not investigated (OPT, Other differences).

## Open questions for you

1. **Are forbid on groups and engine-evaluated conditions needed in year one?** Yes points at B. No leaves A and C, which have forbid on direct subjects (A) or deny-overrides (C), and handle conditions in RLS (G12 9/9 and G13 6/6 pass on all three). Session 4: reframed. B's group forbid goes to the later `cedar_*` model; FGA conditions are the second stage of `fga_*`; neither is in the first spike.
2. **Is uuid-only acceptable?** C requires it and assumes uuids don't collide across principal types (C §12.11). A and B take text and cast to `uuid[]` in RLS (PLAN §4).
3. **Is a global write lock acceptable?** After the optimization this applies mainly to C: 67 tps with 4 clients at 58 ms per nest (pg18 large report). B's lock is held about 0.2 ms for a team of users (6.1k tps), and longer for nesting a sub-tree. Does your app edit teams concurrently, and how big are the teams and sub-trees? Session 4: applies only if C's materialized memberships are adopted later as an optimization of `fga_*`.
4. **Is `repeatable read` refusal acceptable?** B and C raise `0A000` for lock-taking writes. ORMs that default to it would need a different isolation level for permission writes (C §12.3).
5. **Do you need single-branch RLS policies, or is the two-arm projection acceptable as the documented pattern?** It decides how much C's 4.94 ms (against 13.7 for B and 45.6 for A) matters. Session 4: still applies to the `fga_*` tables and to the table that combines RBAC and FGA in the spike.
6. **Are per-document parent links acceptable?** Mirroring a column adds +160 to +385 MB at 1M documents (OPT, Seed time and storage).
7. **Do you want sharing in the first release at all, or `rbac` only?** (Hybrid 3.) Session 4: resolved. The first spike has `rbac_*` and an OpenFGA core subset (Hybrid 3 is not the plan).
8. **If B: should deleting an edge that would leave a shortest path over 10 be rejected (`23514`), or should depth be uncapped?** Today the delete succeeds and silently drops the closure pair, against the rule that the cap is enforced on write. The optimized engine reproduces it on purpose, because the fuzzers compared against the original (B, Remaining hard limits). It is a semantic change, so it is yours to decide. Session 4: matters when Cedar is built on B, not for the first spike.
9. **Is an ignored trailing parameter on `scopes_with_permission` and the list functions acceptable in the public API?** It is what keeps the functions STABLE without plan-time evaluation (finding 1). PLAN §6 says the `rbac` preset API is identical in every design, and the one-argument call is, but the signatures now differ (`boolean` in A and C, `jsonb` in B) and the grants must name them. Session 4: still applies, to the shared toolkit (point 7). The signatures stop being compared across engines because there is no common API.
10. **Carried over from PLAN §9:** the schema name, and a convention for who may grant. Public access (PLAN §9 question 3) is now built and tested on all three (G11 7/7). Session 4: the schema name is still open; the per-model tables live in `permissions`.

## What hasn't been measured

- **Single-client writes in Docker.** OPT's `write_nest_team` runs with 4 clients and includes queueing on the lock. Single-client figures exist only from the design docs, locally on 16.4: C 15.5 ms and B 0.17 ms at large (C §15; B, Original vs final).
- **Nesting a sub-tree, and deletes.** The benchmark nests a 1,000-member team of users. B's cost of nesting a team that contains hundreds of sub-teams (`inner descendants x ancestors` rows under the lock) and C's recompute on revoke or un-nest (25-30 ms at large locally, C §15.2) are not in the benchmark.
- **pg_tle beyond the install test.** `03_tle_install` runs `pgtle.install_extension` + `create extension` as a non-superuser on PG 16, 17 and 18 with pg_tle 1.5.3, and passes for A, B and C (Docker, GOALS G14). Not run: installing through database.dev (`dbdev install`), or on a hosted platform. The benchmarks load the engines with `psql -f`, not through pg_tle.
- **Real hardware and durability.** One Apple Silicon laptop, `fsync=off`, `full_page_writes=off`; every write rolls back, so commit cost isn't measured. The host was not idle during the runs (load average 3-5; OPT, Caveats).
- **Concurrency mixes.** Each workload runs alone. No reads under concurrent membership writes, and no mixed read/write load.
- **PG versions: 16, 17 and 18 are measured, in Docker only.** 16.15, 17.11 and 18.6, large default, medium deep and medium wide, all engines, before and after the optimization ([VER](./bench/baselines/VERSIONS.md), [OPT](./bench/baselines/OPTIMIZATIONS.md)). Results: identical checksums, and the same engine ordering except where noted (wide sharing: A vs B flips between 16 and 17/18). 17 performs like 16; 18 is 10-15% faster on RBAC reads and 21-37% faster on `rbac_update_one` for every engine (VER, What changed between versions). Not measured: small and medium default after the optimization (the small `--check` result in GOALS is pre-optimization); the optimized engines locally on 16.4 in the benchmark's own setup (the design docs' claims were measured at 1 client); a hosted platform.
- **Repeat runs and confidence intervals.** OPT reran 8 configurations once and replaced 4 disturbed ones; the rest are single runs. Also unmeasured: bloat from churn, and checksums beyond 8 sample users.
- **A user who sees most of 1M documents,** and a 1M-element array from `accessible()` (C §11). Sample users see about 20k at large.
- **Large model changes.** C's full `memberships` rebuild at millions of rows (C §12.5); runtime `create_role` churn.
- **B's InitPlan count at scale** (5-7 function calls per table; B, Performance).

## Findings from writing the usage docs

Writing a usage guide for each engine, with every example run as a spec (`test/spec/90_usage_rbac.sql`, `a/90`, `b/90`, `c/90`), turned up these. None of them is fixed in the prototypes; each one is documented on the relevant usage page.

**The `rbac` preset isn't fully identical across engines** (PLAN §6 says it should be):
- `current_subject_id()` returns `text` on A and B but `uuid` on C. On C, a non-UUID JWT `sub` (e.g. `user_2abc`) means no subject.
- C raises `22P02` in `assign_role` for a non-UUID user or scope; A and B accept any text.
- `scopes_with_permission` takes `(text, boolean)` on A and C but `(text, jsonb)` on B, because of the dummy argument. C also has `uuid` overloads of `has_permission` and `has_role`.
- There's no common cleanup call: `delete_subject` (A), `delete_entity` (B), `forget_subject` (C).
- Under `repeatable read`, B refuses `create_role` and `drop_role`; A and C allow them.

**Security-relevant RLS footguns:**
- **A:** the recommended two-arm projection policy ignores a forbid on an individual document, because the folder arm never visits the document. A document-level forbid needs the single-branch shape or a folder-level forbid. Whether C's two-arm policy behaves the same hasn't been checked.
- **B:** a conditioned forbid isn't enforced by RLS until `apply_rls` is re-run, and `lint()` doesn't flag a new `via` type or column.
- **B:** a row with a null parent column is hidden when the user has any denied parent (`not (null = any(...))` is null). Here `can()` says yes while RLS says no.
- **B:** conditions are only partly validated on write. An unknown operator raises at evaluation time, and `rls_expression` then emits broken SQL.
- **B:** the depth cap drops a path after a delete (open question 8), reproduced in `b/90`, which asserts the current behaviour.

**API gaps and quirks:**
- **A:**
  - `grant` is an upsert, so leaving out `p_expires_at` clears the expiry.
  - `grant` doesn't validate the subject type.
  - `revoke` without the subject relation silently returns false.
  - A typo in `from_parent` gives silent no-access.
- **B:**
  - No API to undefine a role, remove an implication or disable a policy.
  - `apply_rls` can't handle non-uuid keys.
  - `explain` can return duplicate rows.
- **C:**
  - `apply_model` loses some rows from its returned plan.
  - Dry runs consume version numbers.
  - `apply_model` skips the `repeatable read` check.
  - No API to list raw grants or purge expired ones.

These are prototype-level issues. Whichever engine is chosen, its list becomes the first hardening work.
